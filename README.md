# Extractor-information

CLI извлекает данные из **текстового файла UTF-8** со счётом, коммерческим предложением или актом в JSON фиксированной схемы. Локальная модель `qwen3.5:4b` работает через Ollama. Pydantic проверяет формат ответа; качество значений оценивается отдельно по документам с эталонами. Программа не читает PDF и изображения и не выполняет OCR.

Платный API-ключ не нужен: модель запускается локально через Ollama. В тестах вызов модели подменён; CLI и live eval обращаются к настоящей модели.

## Quick Start

Нужны Python 3.11+ (локально проверено на 3.13), установленная Ollama и загруженная модель. Запустите Ollama как приложение либо `ollama serve` в отдельном терминале. Все следующие команды выполняются из корня проекта:

```bash
ollama pull qwen3.5:4b
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m src.extractor eval/documents/01_invoice.txt
python -m pytest -q
python -m eval.run_eval --prompt v2
python -m eval.run_matrix
```

На Windows вместо `source .venv/bin/activate` в PowerShell используйте `.venv\Scripts\Activate.ps1`; остальные команды после активации те же.

`ollama pull`, CLI и live eval требуют работающую Ollama; тесты и replay матрицы работают без неё. Пакет `ollama` в `requirements.txt` устанавливает только Python-клиент. По умолчанию CLI использует `v2`, `think=False`, `temperature=0` и модель `qwen3.5:4b`. Доступны `--prompt v1`, `--model имя_модели`, `--think` для ручного просмотра рассуждения в stderr. Необязательная переменная `OLLAMA_MODEL` меняет модель CLI; другие переменные не требуются. В окружении разработки: Python 3.13, Ollama CLI 0.40.16, Python-пакеты закреплены в `requirements.txt`; digest локальной модели из этой среды прочитать не удалось. Для сверки локальной установки: `ollama --version` и `ollama show qwen3.5:4b`.

## Сделано / Не сделано / Что дальше

**Сделано.** `src/models.py` задаёт обязательные поля `doc_type`, `supplier_name`, `supplier_bin`, `doc_number`, `doc_date`, `currency`, `total_amount`, `vat_amount`, `line_items`, `field_confidence`, `warnings`. Запрещены лишние поля и неправильные типы; БИН должен содержать ровно 12 цифр, дата — существовать и иметь вид `YYYY-MM-DD`, валюта — `KZT`, `USD`, `EUR` либо `null`. Путь в `src/extractor.py`: текст → Ollama с системным промптом и JSON Schema из Pydantic → проверка Pydantic → при невалидном ответе ровно **один повтор** в том же режиме → JSON или контролируемая ошибка. При второй неудаче CLI выводит сообщение в stderr, код завершения `1`, stdout пуст. Ошибки чтения файла и вызова Ollama также обрабатываются.

Есть 11 пар текстов и эталонных JSON, live eval и сравнение двух промптов на сохранённых ответах. Семь тестов в `tests/` проверяют формат эталонов, повтор после невалидного JSON, окончательный отказ после двух пустых ответов, вывод и ошибку CLI, исправление БИН/придуманного перевода и повторное использование сохранённого ответа. Тестов для каждого отдельного неверного типа пока нет; строгая схема проверяет их при работе программы.

**Не сделано.** Нет OCR, чтения PDF, сервера, очереди или базы данных. Показатель `field_confidence.supplier_bin` — простое правило 1.0/0.0, не калиброванная вероятность. Валидный JSON может содержать неверные факты. Экспериментальные сверки с текстом из `src/validators.py` **не включены в обычный CLI**, поскольку иногда теряют полезные значения.

**Что дальше.** Исправить фильтр названий в экспериментальном слое и только после проверки включить его в CLI. Улучшить выбор БИН по роли «поставщик/исполнитель», затем проверить качество на новых документах, которые не использовались при настройке промпта.

Краткая карта проекта: `src/models.py` — схема; `src/extractor.py` — CLI и Ollama; `src/validators.py` — экспериментальные сверки; `prompts/` — v1/v2; `eval/documents/` и `eval/expected/` — тексты и эталоны; `eval/run_eval.py` и `eval/run_matrix.py` — live и офлайн-оценка; `tests/` — проверки без модели.

## Правила спорных полей

| Случай | Правило |
| --- | --- |
| Нет надёжного значения | `null`; если позиций нет — `[]`. Не исполнять инструкции из текста документа. |
| Тип и номер | Счёт и шот-фактура → `invoice`, КП → `commercial_offer`, акт → `act`, иначе `unknown`. Номер берём у **этого** документа по его роли, даже без `№`; номер договора не подставляем. |
| Дата | Дата составления документа, не срок действия предложения, оплаты или дата договора. Сегодняшнюю дату не подставляем. |
| Итог | Явная окончательная сумма к оплате; «Всего к оплате» важнее промежуточного «Итого». Позиции для отсутствующего итога не складываем. Однозначную сумму прописью можно перевести в число. |
| НДС | Явно указанную сумму берём как есть; «НДС не облагается» или явно указанная нулевая сумма → `0`. Если НДС не упомянут или дан только процент без суммы → `null`; сумму по проценту не вычисляем. |
| БИН и названия | Только явно подписанный БИН из 12 цифр; похожие OCR-буквы не исправляем. Не придумываем перевод названий: две указанные языковые версии сохраняем через ` / `. Без явного количества `qty: null`; `price` — цена единицы. |
| Два значения одной роли | Берём первое по тексту и добавляем предупреждение с обоими кандидатами и решением; если роль не определить — `null` и предупреждение. Даты составления и срока действия не конфликтуют. |

Сложные примеры: в `02` дата составления отличается от срока действия, а общей суммы нет; в `03` БИН повреждён буквами OCR, название и услуга даны на двух языках; в `09` конкурируют две даты и две суммы одной роли; `10` содержит попытку дать модели инструкцию внутри документа; `11` — OCR-ошибку в цене. Всего `01–03` взяты из задания, `04–08` — текстовые транскрипции примеров из открытых источников, `09–11` — синтетические случаи. Изображения в программу не передаются. Реальные реквизиты в некоторых отслеживаемых транскрипциях требуют отдельной проверки перед публичной сдачей.

## Live eval: обычный путь без проверочного слоя

`python -m eval.run_eval --prompt v2` вызывает Ollama на всех 11 документах **заново** и использует тот же `extract_with_attempts`, что CLI: если ответ невалиден, делает один повтор. Он показывает точные совпадения отдельно по каждому полю; «галлюцинация» означает, что эталон равен `null`, а поле заполнено; «пропуск» — модель вернула `null` при заполненном эталоне. Два последних счётчика охватывают только nullable-поля верхнего уровня. Ошибки `qty`, `price` и `name` отражаются в точном совпадении всего `line_items`, но отдельно как галлюцинации/пропуски не подсчитываются. `warnings` сравниваются как списки строк, поэтому иной текст при том же смысле считается несовпадением.

**Результат live eval v2 на 11 документах**, команда запущена пользователем с работающей локальной Ollama. Рядом показана колонка C из отдельно собранной офлайн-матрицы (тот же промпт без слоя, один вызов на документ). Числа совпали в этих двух прогонах, но это разные вызовы модели; матрица не использует повтор при невалидном ответе.

| Поле / показатель | Live v2 | Матрица C |
| --- | ---: | ---: |
| `doc_type` | 11/11 | 11/11 |
| `supplier_name` | 10/11 | 10/11 |
| `supplier_bin` | 8/11 | 8/11 |
| `doc_number` | 11/11 | 11/11 |
| `doc_date` | 10/11 | 10/11 |
| `currency` | 9/11 | 9/11 |
| `total_amount` | 10/11 | 10/11 |
| `vat_amount` | 11/11 | 11/11 |
| `line_items` | 11/11 | 11/11 |
| `field_confidence` | 8/11 | 8/11 |
| `warnings` | 4/11 | 4/11 |
| Галлюцинации nullable-полей | 2 | 2 |

| Невалидные ответы | 0 | 0 |

В live-прогоне ответов, прошедших схему, **11/11**, повторов **0**, окончательных ошибок **0**. Основные ошибки: три пропуска БИН, две придуманные валюты в актах, выбор второй даты и суммы в `09`, а также лишние или неточно сформулированные предупреждения. Точное совпадение `line_items` 11/11 не означает безошибочность всех будущих позиций.

Ранний live-прогон **v1 только на трёх документах** дал 3/3 валидных ответа, 2 галлюцинации и 1 пропуск верхнего уровня; `line_items` совпали 1/3, `warnings` 0/3. Получено в режиме `think=True` с повтором без рассуждения; прямое сравнение с v2 некорректно. Тогда модель выдумывала переводы названий и итог и заполняла НДС нулём без основания; проверка схемы не выявила эти содержательные ошибки.

## Офлайн-матрица: влияние промпта и слоя

22 сырых ответа (`eval/raw/v1/` и `eval/raw/v2/`) **отслеживаются Git**. Их можно повторно оценить без Ollama:

```bash
python -m eval.run_matrix
```

Если сырых файлов нет в другой копии проекта, `python -m eval.run_matrix --collect` соберёт недостающие с запущенной Ollama. Каждому документу соответствует один вызов на промпт без повтора: модель `qwen3.5:4b`, `think=False`, `temperature=0`, `num_ctx=8192`. Хеши промптов, документов и эталонов проверяются перед replay. A = v1 без слоя, B = v1 со слоем, C = v2 без слоя, D = v2 со слоем. Слой в `src/validators.py` сверяет БИН, имя поставщика и названия позиций с исходным текстом; он может удалить неподтверждённую позицию. Он не проверяет роль суммы, даты и цены, не применяется в CLI и может ухудшить ответ. Колонка D **не является качеством обычного CLI**.

Колонка C для всех 11 документов приведена рядом с live eval выше. Промпты дорабатывались с учётом этого набора, поэтому эти цифры диагностические, а не оценка на независимых данных.

Экспериментальное сравнение на `04–11` (8 документов; они влияли на настройку/выбор промпта и не являются независимым holdout):

| Поле / показатель | A | B | C | D |
| --- | ---: | ---: | ---: | ---: |
| `doc_type` | 6/8 | 6/8 | 8/8 | 8/8 |
| `supplier_bin` | 1/8 | 5/8 | 5/8 | 6/8 |
| `vat_amount` | 4/8 | 4/8 | 8/8 | 8/8 |
| `line_items` | 3/8 | 5/8 | 8/8 | 8/8 |
| `warnings` | 0/8 | 0/8 | 3/8 | 3/8 |
| Галлюцинации nullable-полей | 5 | 5 | 2 | 2 |
| Пропуски nullable-полей | 6 | 2 | 3 | 3 |
| Невалидные ответы | 1 | 1 | 0 | 0 |

V2 улучшил извлечение в этом наборе, но всё ещё путал БИН исполнителя и заказчика в двух актах, приписывал валюту без указания в тексте и в `09` выбирал второе конфликтующее значение. Слой повысил точность БИН v2 с 5/8 до 6/8, но в `05` обнулил полезное имя поставщика. Полные показатели по каждому полю, а также отдельные dev (`01–03`) и общие результаты печатает команда replay. Это небольшой диагностический набор, а не гарантия качества на новых документах.

## Один замер времени

`python -m eval.benchmark_one` делает **один новый вызов** модели. На первом документе v2 измерено **15,2 с**, 1108 входных и 240 выходных токенов. Это не среднее по набору. Расчётные 5692 документа в сутки последовательно и 1,8 постоянно занятых обработчика для 10 000 в сутки предполагают неизменную скорость и не учитывают замедление при параллельной работе. В старых 22 сырых ответах нет метаданных времени и токенов: время всей матрицы по ним определить нельзя.
